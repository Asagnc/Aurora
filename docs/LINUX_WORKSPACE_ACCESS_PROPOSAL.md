# Root Linux 会话文件访问方案（已确认，2026-10-22）

用户已于2026-10-22明确选择“采用推荐的Root批量文件通道”。0.1.28已替换0.1.27验证路径；当前实现与限制见LINUX_ROOT_FILES.md。下文比较保留为决策依据。

## 问题与当前实现

0.1.27内部派发链路已接通。为先闭合“退出确认→文件可访问→释放租约”，当前内部验证路径在退出后对.aurora-linux会话目录进行一次不跟随链接的属主/权限恢复。尚未开放Agent任意Linux命令，也没有真机或性能结论。这种全目录遍历随文件数增长，不适合作为大量源码、逆向产物或编译缓存的默认路径。

此前批准的LINUX_OWNERSHIP_PROPOSAL.md决定的是共享Root/PRoot环境代属主。本项新增决定Root guest写出的会话文件如何供Agent/UI访问和删除，不重新审批环境代方案。

## 方案比较

| 方案 | 命令结束成本 | 文件访问与删除 | 适用性 |
| --- | --- | --- | --- |
| 每次归还App属主 | 扫描整个会话Linux目录，并执行元数据操作 | 普通App文件通道可直接访问 | 简单；目录规模增加会拖慢每个命令，也改变原Linux属主/权限 |
| user namespace / idmapped mounts | 可避免逐文件改属主 | 依赖实际内核、文件系统及命名空间资格 | 适合作为未来可验证优化；当前不能当跨Root设备的硬依赖 |
| 保留属主，内置Root批量文件通道（推荐） | 确认scope退出，更新少量运行元数据 | Agent/UI按需批量读、写、列目录；删除Root区域时由Root执行 | 不在每条命令后扫描全部文件；需增加内置文件通道与Root撤权后的待清理状态 |

## 推荐落地

保留.aurora-linux中的真实属主和权限。Agent沿用文件工具语义，由Aurora根据文件所在区域分派；Root通道一次处理批量读取/编辑/元数据，内容按预算或文件描述符传输，不逐行日志IPC。Root服务已存在，不新增常驻进程、轮询、第三方App或逐会话rootfs副本。

命令结束只做进程/挂载资格确认、运行标记更新与租约释放；不做会话全树chown。任务失败、超时和断连保持同一退出确认规则。共享镜像与正在使用的其他会话不会由文件通道清理。

用户查看Root文件时也走该通道，仍显示详情。Agent要发送图片或用户导出文件时，仅把选定产物发布到现有App可读产物区；按需解码/复制，不搬整个目录。会话删除需要Root清理其Root区域；Root不可用时保留“待删除”，重新连接后继续，不能假装已删除。

## 验收标准

每个正常命令结束不触发会话全树遍历或chown；小/大源码树对照测量收尾成本。批量文件通道验证链接、路径、取消、内容预算与Root撤权；对损坏或失联保留恢复记录。验证Root图片发布、对话删除/重启继续清理，以及其他会话和共享版本不受影响。通过后再替换当前内部验证路径并开放Agent入口。

## 依据与边界

- Linux内核idmapping说明：https://docs.kernel.org/filesystems/idmappings.html 。内核/挂载映射提供属主转换机制，不能以普通chown冒充。
- Docker userns-remap官方说明：https://docs.docker.com/engine/security/userns-remap/ 。该机制需要UID/GID映射与宿主文件权限配合，外部挂载有适配成本；不是可直接套用的Android通用资格。
- Linux flock：https://man7.org/linux/man-pages/man2/flock.2.html 。当前启动锁复用继承的open file description，作为scope日志出现前的恢复屏障。
- SQLite外键：https://www.sqlite.org/foreignkeys.html 。运行记录与租约在既有SQLite事务中一起写入，外键阻止提前删除租约。

推荐第三项是针对Aurora的工程判断；尚无真实工作负载的领先性能结论。用户确认后已实施Root批量文件通道，已删除每条命令收尾的递归属主恢复；尚待Root真机资格和性能测量。
