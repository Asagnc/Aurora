# chroot/PRoot 环境属主方案（已确认）

2026-10-22。现有Ubuntu解包保持App UID，目的是保留Android标签和普通UID管理能力；entries.json保存原始UID/GID，但尚未恢复。这不是可直接宣称完整chroot语义的状态。

## 实际发现

固定官方ARM64包6648条（含根目录），普通文件原始字节113253544（约108MiB，不含文件系统块/目录/日志）。原始属主组合为(0,0)6640、(0,42)6、(42,0)1、(0,8)1。不能把所有文件映射到Root0就声称完整保留。直接chown现有共享环境会改变PRoot与App文件访问；普通UID可能无法读取0600或删除Root目录，且不能改动正在使用的环境。

## 推荐

同一官方镜像按需发布不同后端的共享环境代：Root chroot代恢复原始UID/GID/权限，普通PRoot代保留App UID；每种代由所有会话共享，不逐会话复制。Root用户默认只准备Root代，不预装两套；只有明确需要并且PRoot资格通过时才额外准备普通代。Root代使用Root管理发布/清理；撤权时显示暂不可用，绝不盲改权限。旧的App UID环境仍按租约保留，空闲后再清理，不原地改属主或覆盖活动版本。

成本：若选择同时保留两种代，基础文件字节会多约108MiB，加目录/块开销；首次只装Root代无需预装两份。实际使用量和准备峰值必须显示。环境更新/变体准备可按已批准策略探测reflink，但不能保证手机文件系统支持，也不能用可写硬链接伪造隔离。

## 比较

- 直接chown共用树：简单但破坏普通访问、清理与活动环境，不推荐。
- 单一只读App UID树直接chroot：能够运行部分程序，但属主语义不完整，不能称最优完整环境。
- idmapped mount：依赖额外内核/文件系统能力；统一App UID已丢失逐文件属主差异，单一映射不能还原多种原始UID/GID。不能当通用无成本修复。
- OverlayFS metacopy：可减少元数据修改的数据复制，仍依赖实际内核/xattr/文件系统及清理资格。按既有方案保留未来可选优化，不升级成所有设备硬前置。
- 两种后端按需各自共享代：固定语义、没有逐会话复制，也能明确报告空间/权限成本；推荐。

用户已确认“采用推荐方案”；此项不需重复确认。改变共享环境后端布局与Root清理要求按分阶段实现验收，未完成前不声明可用。私有挂载/只读bind/chroot与退出清理的独立资格测试可先继续，不修改现有镜像属主、不开放业务命令。
