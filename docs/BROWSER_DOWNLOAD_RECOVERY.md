# 下载中断恢复（0.1.40）

2026-10-23。沿用已批准的会话文件/现有SQLite账本恢复分工，无新网络栈、守护进程、数据库表或重放队列。

## 已实现

1. 下载先生成并登记 runs/<UUID> 目录，再排他创建 download.bin.partial。数据库登记失败、取消或进程退出在文件创建之前发生时，不会留下未登记的新下载文件。旧版登记前创建的历史窗口不能靠新流程追溯证明，缺失关联的旧文件仍保留给显式检查/删会话。
2. 应用进程恢复先沿用 recoverInterruptedRuns 标记 started 为 uncertain；随后最多处理64条符合条件的下载。后续会话Agent开始前也只补该会话最多64条。没有定时轮询、目录遍历或网络重试。
3. 条件：browser_download、uncertain、原 result 为空、已有有效产物目录、会话非删除中。普通进行中的任务、其他工具、其他会话的定向调用不受影响。恢复调用点在旧浏览器进程退出后，或当前会话上一轮任务已收尾后；不是给任意调用者操作活跃写入器的API。
4. 对根路径、runs、选定UUID目录和目标条目逐层检查链接/类型；只 unlink 选定目录的固定普通文件 download.bin.partial。已发布 download.bin、同级其他文件、目录、未登记目录、符号链接与异常条目保留。没有重新创建不存在的会话空间，也不为此请求Root。
5. 成功检查/清理后，条件更新原为空的 result，记录 interrupted、结果仍未知和 partial_removed/published_retained/absent；state 始终 uncertain，不改为completed，不证明服务端动作成功，也不覆盖已有结果。会话Agent重载这部分详情。
6. 在unlink后、记账前再次退出可幂等重试。失败/类型不明记录保持未处理，下次可重试。批次成功记录退出待处理集合，后续批次可继续；若前64条持续不明，后面的记录可能等待人工检查，不宣称全部历史垃圾总能自动清空。

## SQLite查询成本与迁移

- schema 6→7只新增待回收下载的部分索引 browser_download_pending，不加列/表，不重写消息或协议原生历史。旧1–5迁移路径先执行原有建表/加列逻辑，再加索引。
- 索引只包含指定tool/state/result/产物条件的行，按owner及隐含rowid读取；回收结果写入后该行离开索引。查询明确使用该索引，按会话主键校验未删除；先在待处理索引中取最多64个候选，再过滤删除中的会话；不把外层 LIMIT64 错当扫描64条历史的保证。
- 首次升级建索引仍有一次历史索引构建成本，不宣称零升级IO。常态查询的索引形状根据 [SQLite官方部分索引合同](https://www.sqlite.org/partialindex.html) 与本机实际计划验证。
- Python宿主SQLite3.50.4使用从生产Kotlin提取的条件/SQL片段，种入10000条完成历史及1条待处理：全局读取52条VM指令、按会话65条，均用待处理索引，无临时排序。额外种入10000条属于删除中会话的待处理项，全局窗口只检查64候选（1426条VM指令），定向正常会话仍可继续。若窗口全被删除中的会话占据，正常会话会在其Agent开始时定向补处理。这是主机形状验证，不是Android延迟/耗电结论。
